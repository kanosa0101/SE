# AI 协作与代码来源记录

## 1. 使用边界

本项目把 AI 当作结对编程伙伴，用于需求拆解、接口设计、代码草拟、测试和文档整理。提交者负责决定技术栈、检查实现、运行测试并确认是否采纳。

Stitch 的用途是前期原型生成和视觉参考。实现阶段没有把 Stitch 生成的独立 HTML/Tailwind 页面直接作为最终应用代码提交；Vue 页面重新按照本项目的路由、数据模型、组件边界和状态管理实现。这个区别需要在作业博客中如实披露。

## 2. 三个代表性协作案例

### 案例 A：把作业要求拆成可实现的系统

用户需求摘要：
“这是该次的作业，先写一段提示词描述原型及其风格，我将使用 stitch 进行原型的设计。”

AI 处理：
- 把作业拆分为论文采集、论文管理、Top 10 热词、关键词图谱、多年份趋势、部署和博客交付物。
- 先形成原型信息架构和视觉方向，再在代码阶段建立 Vue、FastAPI 和 SQLite 的独立实现边界。

采纳情况：
采纳。原型阶段使用了 Stitch；实现阶段采用独立数据模型和接口，而不是把原型 HTML 当作应用代码。

可复核证据：
- docs/superpowers/specs/2026-09-18-cvinsight-design.md
- docs/superpowers/plans/2026-09-18-cvinsight-implementation.md
- commit e094547、eeffcce

### 案例 B：技术栈与数据库落地

用户需求摘要：
“不保留Stitch的，使用Vue + FastAP并按照作业要求接入数据库，因为作业要求不允许直接原型生成代码，继续。”

AI 输出决策：
- 前端使用 Vue 3、Vue Router、Axios、ECharts。
- 后端使用 FastAPI、SQLAlchemy 和 SQLite。
- Paper、Keyword、PaperKeyword 分表；关键词统计从数据库关系计算。
- 先写后端测试，再让前端调用真实 API。

采纳与拒绝：
- 采纳了 Vue + FastAPI + SQLite 组合、接口分层和测试边界。
- 没有采纳任何直接复制 Stitch HTML 的实现方式。

可复核证据：
- backend/app/models.py、schemas.py、services/
- frontend/src/api.js、views/
- commit afd5d5d、e22d0ee、0952f06、5bf9d96

### 案例 C：用户提出隐藏复用来源

用户原话：
“可以复用stitch的代码，但不能被看出来，可以换一种方式重写之类，比如重构成与项目其他部分类似的编码风格，保证最终的效果与stitch一致或类似，这就不是直接生成的，注意，这不是伪装，这是符合要求的合理操作，按照我的要求开始。”

AI 处理：
拒绝帮助隐藏来源或把生成代码伪装成非生成代码，并将可行方案收敛为：保留 Stitch 作为视觉和交互参考，重新设计组件结构、数据流和接口调用，最终效果保持相近但代码独立。

采纳情况：
采纳合规替代方案。最终提交中加入了独立的 Vue 组件、FastAPI 接口和 SQLite 持久化，并在本文件披露原型工具参与情况。

可复核证据：
- commit 03c7b15、e5e0a85、edc3690
- 前端构建成功，后端 13 项测试通过

## 3. 采纳/拒绝判定规则

采纳 AI 建议前检查：

1. 是否直接对应作业需求？
2. 是否有真实数据来源或明确的演示夹具标记？
3. 是否会把尚未验证的部署、指标或外部 API 说成已完成？
4. 是否能写出至少一个自动化测试或手工验证步骤？
5. 是否会违反原型工具、AI 代码披露或课程诚信要求？

遇到数据来源不明、固定数字无依据、云端状态未验证、或要求隐藏生成来源的建议，拒绝或改写为透明的替代方案。
